六种模式分别在做什么
模式	当前示例的流程	谁决定下一步	适合处理
ReAct	用户提问 → 模型判断是否调用工具 → 工具返回结果 → 模型继续回答	模型按需选工具或结束	需要查数据、调用 API、执行计算的交互任务
Self-Ask	拆成子问题 → 逐个回答 → 综合	初始拆解由模型完成，之后按序逐题回答	需要多项信息才能回答的复杂问题
Reflection	生成初稿 → 审查 → 必要时修订 → 再审查	规则控制是否继续修订	需要提升质量、减少遗漏的内容生成任务
Router	分类问题 → 选择一个专家分支 → 该专家回答	分类器选分支	用户请求类型明确、可以交给不同处理器的系统
Workflow	分析 → 提纲 → 初稿 → 审查 → 定稿	预先写好的流程	输入和处理步骤相对固定的业务流程
Multi-Agent	分析、风险审查、行动建议并行 → 编辑整合	预设角色分工；编辑负责整合	同一问题需要多个视角或专业角色的任务

1. ReAct：边判断边使用工具
react.py 给模型提供 get_today 和 add_numbers 两个工具。模型看问题后自行决定是否调用其中一个或多个工具，再基于工具结果作答。

它的重点不是固定计划，而是根据中间结果选择下一步动作。例如“今天几号并计算 12.5 加 7.5”，模型可以调用日期工具和加法工具；如果问题不需要工具，也可以直接回答。

适合：

查询数据库、搜索网页、调用 API。
根据工具返回结果决定是否继续查询。
用户请求变化较大，无法提前写死所有执行步骤。
代价与风险：

工具调用次数、执行时间不容易完全预测。
模型可能选错工具或提供不合适的参数。
工具需要做权限、输入校验、超时和错误处理，不能只依赖 prompt。
2. Self-Ask：先拆出要回答的小问题
Self-Ask.py 先把原问题拆成最多 4 个子问题，再逐一回答，最后汇总。它的示例会在回答后续子问题时带上之前的回答，因此当前实现是顺序回答，不是并行搜索。

例如回答“团队为什么该用 Git”，可以先分解为：Git 解决什么问题、核心工作方式是什么、适合什么场景，再综合回答。

适合：

问题涉及多个彼此相关的方面。
最终结论依赖几项前置解释或事实。
希望让复杂问题的覆盖范围更完整。
代价与风险：

拆分质量决定后续质量，漏掉关键子问题就可能得到片面的总结。
顺序调用会增加延迟和模型调用成本。
当前代码通过解析编号列表取问题，模型若没按格式输出，会退化为只回答原问题。
3. Reflection：先产出，再批评和修订
Reflection.py 先生成初稿，再让审查者检查事实性、完整性、可执行性和表达；若审查认为需要修改，就修订后再审查。最多修订 2 次。

它不是简单的“多写一遍”，而是建立了一个质量反馈循环。但是审查者和作者仍可能共享相同模型的盲点，所以 Reflection 不等于事实核查或人工审核。

适合：

报告、方案、说明文档等需要较好完成度的文本。
初稿经常遗漏要求，需要显式检查清单。
可以接受额外模型调用来换取更完整的输出。
代价与风险：

每轮审查和修订都会增加延迟与成本。
审查意见可能含糊或错误，修订反而引入新问题。
当前程序用是否出现固定短语“没有需要修改的问题”决定终止，判断比较脆弱；并且最终结果保存在 draft 字段中，answer 字段没有实际参与流程。生产使用时适合改成结构化审查结果和明确的通过条件。
4. Router：分类后只走一条路
Router.py 先把问题分类为 coding、learning 或 general，然后条件边只调用对应专家。它和 ReAct 的差别在于：Router 的核心动作是选处理路径，不是让同一个助手不断挑工具、观察结果再决定。

适合：

支持请求类别有限、分类边界比较清楚的客服或内部助手。
不同类别需要不同提示词、工具集、权限或模型。
希望让各处理分支独立测试和维护。
代价与风险：

分类错了，用户就会进入错误分支。
现在三个专家都用同一个 Ollama 模型，只是角色提示不同；这是一种简单的专家分支示范，不代表不同的模型或真正独立的专业能力。
分类输出是普通文本，解析失败时会回退到 general；真实系统可以用结构化输出、置信度和澄清问题改善路由。
5. Workflow：步骤事先确定，按顺序执行
Workflow.py 将内容生成分成分析、提纲、初稿、审查、定稿五个节点，每一步读取共享 state 中上一步的结果。与 Self-Ask 的主要区别是：Workflow 的步骤是按任务流程预先设计，不是先让模型把问题拆成任意子问题。

适合：

流程稳定、输入输出清晰的任务，例如文档处理、审批准备、标准化报告生成。
希望可预测、容易测试、能够追踪每一步产物。
某些步骤必须按顺序完成，不能跳过。
代价与风险：

灵活性较低，遇到流程外问题不能自动调整步骤。
每个节点都调用模型时，会产生固定的调用成本。
当前示例审查后总会进入定稿节点，没有“审查不通过就返工”的条件边。因此它演示的是“固定流水线中的审查”，而不是带质量门禁的循环流程。
6. Multi-Agent：多个角色分别处理，再综合
Multi-Agent.PY 让分析员、风险审查员和执行顾问处理同一个问题，最后由编辑整合三份结果。LangGraph 中三个角色从开始节点分出，编辑节点等待它们都完成后再运行。

它和 Workflow 的差别是：Workflow 通常是同一条任务链上每步做不同加工；Multi-Agent 通常是多个角色从不同角度并行产出，再合并结果。

适合：

一个方案需要同时评估收益、风险和执行步骤。
多个子任务互相独立，可以并行处理。
希望在最终答案里体现观点对照，而不是只让一个模型单线完成。
代价与风险：

多个角色会增加模型调用次数和总成本。
并行会缩短等待时间，但也更依赖模型服务的并发能力。
不同角色可能重复、矛盾或各自带有偏差，整合节点要能处理冲突。
当前角色只是用不同 prompt 调用同一个模型，不是不同模型、独立记忆或不同工具权限的完整多智能体系统。
容易混淆的几组
Router 和 ReAct
Router 回答“这类请求交给谁处理”；ReAct 回答“为了完成当前请求，下一步要不要用工具、用哪个工具”。可以组合：先 Router 分到技术支持，再由技术支持的 ReAct agent 调用文档搜索工具。

Workflow 和 Self-Ask
Workflow 的步骤由开发者预先定义，重点是可靠执行固定流程；Self-Ask 的子问题由模型根据输入生成，重点是拆解复杂问题。Workflow 更可控，Self-Ask 更灵活。

Reflection 和 Multi-Agent
Reflection 是同一份产物经过“作者—审查—修订”的迭代；Multi-Agent 是多个角色从不同视角给出并行结果，再整合。Reflection 更像质量闭环，Multi-Agent 更像多视角协作。也可以组合：多角色先评审，再让作者修订。

Workflow 和 Multi-Agent
Workflow 描述任务步骤；Multi-Agent 描述角色分工。两者不冲突：可以先按 Workflow 定义步骤，再让某一步由多个 agent 并行完成。

实际怎么选
需要模型自行选择 API、工具或数据查询：选 ReAct。
问题需要拆成几个必要部分再合并：选 Self-Ask。
已经有初稿，质量还要检查和改进：选 Reflection。
不同请求类型需要不同处理路径：选 Router。
任务流程固定，强调可控、可追踪：选 Workflow。
同一个问题需要多个独立视角：选 Multi-Agent。
一句话记忆：ReAct 选动作，Self-Ask 拆问题，Reflection 改质量，Router 选分支，Workflow 固定步骤，Multi-Agent 分角色。
